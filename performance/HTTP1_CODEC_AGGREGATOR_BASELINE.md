3. 因为真实基线整体更低，所以后续轮次的意义应改写为：先确认 codec 已被大幅推过，再继续收敛 aggregator 剩余边界。

## 第一轮

改造：

- 修复 chunk trailer header 惰性切片的生命周期错误，恢复 `HttpRequestDecoder` / `HttpResponseDecoder` 在分片 trailer 场景下的正确性。
- 将请求/响应 header line 的所有权直接转交 `DefaultHttpHeaderEntry`，减少 header 热路径上的 `retain -> free` 往返。
- 用联合 exploratory benchmark、stack profiler 与 JFR 录制确认当前热点仍主要停留在 `HeaderEntryStore.ensureAppendCapacity`、`QueueByteBuf` 组件拼装、`Http*Decoder.decodeHeaders` 与 `Http*Aggregator.emitAggregated` 路径。

2. `解码大响应`、`编码简单请求`、`编码 POST 请求` 与 `编码简单响应` 的提升最夸张，说明 codec 主路径在第一轮就已经完成了对旧实现的大幅跨越。
3. Aggregator 在第一轮同样获得了 33%~52% 的吞吐提升，并把分配压低约 70%；但即便这样，和 Netty 的实时对比仍未全部转正，所以后续重点仍然应放在 aggregator 吞吐边界。

## 第二轮

改造：

- 在 `HttpRequestAggregator.RequestHeaderSnapshot.capture(...)` 中改为单次扫描 `DefaultHttpHeaders.headerEntries()`，减少请求聚合阶段对 `Content-Length / Expect / Connection` 的重复查找。
- 修正 `HttpRequestAggregator.emitAggregated(...)` 中 request 路径 `declaredLength` 传播缺口，让已知 `Content-Length` 的请求重新命中预分配连续 content buffer，而不是退化到 `appendContent -> CompositeByteBuf`。
- 用 JFR 复核 `aggregateLargeRequest`：`DefaultFullHttpRequest.appendContent(...)` 已退出主热点，剩余首要热点收缩到 `QueueByteBuf.sliceLineView/readLineBuffer` 与 `HttpRequestDecoder.decodeHeaders(...)` 的跨分片 header line 处理。

2. `聚合 POST 请求` 也同步提升到 `142,854.597 ops/s`，说明 `Content-Length` 已知请求的预分配路径恢复后，对 request-side aggregator 吞吐有普遍正收益。
3. 第二轮并没有把 aggregator 全部拉过 Netty：当前仍落后的 3 项集中在 `聚合大请求`、`聚合 POST 请求`、`聚合大响应`，而 JFR 指向的下一瓶颈已经从 content assembly 收缩到 fragmented header line 解码。

## 第三轮

改造：

- 在 `HttpRequestDecoder.decodeHeaders(...)` 中把 request-side `Expect / Connection` 顺手写入 `HttpContext.RequestDecodeState`，避免聚合器为了这两个 header 再次 materialize / 扫描 staged header block。
- 在 `HttpRequestAggregator.onHeadersStaged(...)` 中移除 `peekEachMessage -> RequestHeaderSnapshot.capture(...)` 这次额外的 staged queue 遍历，直接复用 decoder state 中已经解析好的 `contentLength / expect / connection`。
- 在 `HttpRequestAggregator.emitAggregated(...)` 与 `HttpResponseAggregator.emitAggregated(...)` 中，把 decoder state 的 `contentLength` 作为 `declaredLength` 首选来源，仅在缺失时才退回到 `mergedHeaders.getLong(...)`，减少 request/response 聚合阶段的重复 header 查找。

1. 这一轮真正保留下来的收益来自“**复用 decoder 已经知道的 header state**”，而不是继续对 `QueueByteBuf` 或 header-name fast path 做微调；前者给 request/response aggregator 都带来了可复现的正收益，后者在 focused run 里都验证为负收益并已撤回。
2. Aggregator 四项吞吐全部继续抬升，其中 `聚合大请求` 提升到 `110,361.985 ops/s`、`聚合大响应` 提升到 `122,407.077 ops/s`、`聚合 POST 请求` 提升到 `148,498.488 ops/s`；尤其 `聚合大请求` 的分配从 `4,814.803` 下降到 `4,638.759 B/op`，说明重复 header 扫描确实还在 request 聚合路径上留下了可见成本。
3. 第三轮之后，联合 full run 的实时对比已经把 `聚合简单响应` 稳定拉到 Netty 之上，但 `聚合大请求`、`聚合 POST 请求`、`聚合大响应` 仍未完全转正；下一轮瓶颈仍应继续沿着 fragmented header line / decoder-header object 税这条链路深入，而不要回到已验证为负收益的 generic micro-tuning。

当前结论：

1. 用真实基线回看，当前主干的进展幅度继续扩大：codec 7 项吞吐相对基线已提升 **+129% ~ +281%**，分配下降 **-75% ~ -89%**，并且 7 项都稳定高于同次 Netty。
2. Aggregator 相对真实基线也已来到 **+53% ~ +63%** 的吞吐提升区间，分配下降约 **-69% ~ -72%**；其中 `聚合简单响应` 已稳定越过同次 Netty，但 `聚合大请求`、`聚合 POST 请求`、`聚合大响应` 仍是最后 3 项未转正场景。
3. 第三轮证明，继续沿着“复用 decoder 已解析状态、减少 staged headers 重扫”这条线是有效的；下一轮正式优化仍应继续聚焦 fragmented header line 解码与 `DefaultHttpHeaderEntry`/header object 税，而不要回到已验证为负收益的 generic `QueueByteBuf` / header-name micro-tuning。
