日期：2026-04-22
最后更新：2026-09-30（round101：HTTP 字段查询调用边界与 ASCII 比较）

## 基准环境与口径

- 初始历史基线：macOS / Intel i9-9880H / JDK 17.0.4。跨机器、跨基准版本的百分比仅供历史趋势参考，不能用于归因本轮改动；初始历史基线不重置。
- 当前环境：WSL2/Linux / JDK 17.0.2 / JMH 1.37 / Netty 4.1.107.Final；单线程，固定 CPU 30、31。最终全量保持 `-wi 3 -i 5 -w 1s -r 2s -f 1 -prof gc -foe true`，原有 25 组及 header 语料 5 组，共 30 对、60 条方法与参数组合。本轮所有普通配对实验也使用同样 wi3 参数。
- ops/s 越高越好；B/op 是每次操作的堆分配量，不等于 RSS、堆外常驻内存或池中保留容量。吞吐误差为 JMH 99.9% 区间半宽；独立 fork 的配对均值不是 JMH 原生多 fork 汇总，不合成置信区间。
- 通道生命周期按源码区分：HTTP 编解码/聚合及 WebSocket 帧/消息基准双方在 Trial 创建并复用通道；WebSocket 握手双方在每个 Invocation 创建、关闭通道，Neta 的 NetManager 在 Trial 复用。Neta 仍使用 receiveDataAndReturning / sendDataAndReturning 同步协议栈入口，普通数据输出直接返回，不经过传输队列和 PlayLoad 订阅分发；握手内部 fireEvent 产生的协议事件仍走事件分发。这不是完整虚拟传输或真实 socket 端到端吞吐。本轮未改变报文字节、Netty 配置、计时方法、泄漏检查或虚拟通道。
- 四字段读取沿用 round84 修正后的[基准](src/main/java/net/hasor/neta/http/HttpCodecBenchmark.java)：双方解码相同字节，读取 Host / Accept / Accept-Language / Connection 并累计 String.hashCode，再纯释放结果。聚合 POST 仍为 19/27/23/31/17/147 bytes 六包，总长 264，正文起点 154、长度 110，正文全部位于最后一包，不是多块正文复制基准。
- [header 语料](src/main/java/net/hasor/neta/http/HttpHeaderCorpus.java)仍为普通、同长度自定义、混合大小写 POST、四段 chunked 请求及响应五组，每组轮换 16 条报文、每条 12 个字段；双方字节、顺序和分包一致，计时不读取全部字段。[语料测试](src/test/java/net/hasor/neta/http/HttpHeaderCorpusTest.java)另行核对字段、正文和结束标记。本轮没有新增特定名称、长度或报文白名单。
- WebSocket 的部分输入准备位于 Invocation 夹具，JMH 主吞吐使用 realTime 排除该夹具时间，但 gc.alloc.rate.norm 包含迭代内 Invocation 的准备与清理分配。共用状态同时准备文本和二进制输入，未消费对象也在清理中释放，因此 B/op 不是仅 Benchmark 方法体的分配。沿用[生命周期核对](build/round96-lifecycle-audit.json)。Neta 帧基准还保留既有 ReadyWebSocketBinder 透传节点，Netty 仅安装帧 decoder；这是已有基准工作量差异，不是本轮新增，也未通过删除它来抬高本轮成绩。

## 结论与下一轮优化

- **全量结果**：吞吐均值 28/30 高于 Netty，其中 HTTP 15/17、WebSocket 13/13；B/op 30/30 更低。解码简单请求 -3.93%（区间重叠）；解码简单请求并读取四个头字段值 -3.03%（区间重叠）。领先项中 25 项双方区间不重叠；单 fork 均值不等于真实负载稳定全面领先。本轮没有保留新的生产性能改动，最终产物与 round100 完全相同；本次全量变化不是新增代码收益。
- **重点位置**：解码简单请求并读取四个头字段值 -3.03%（区间重叠）；聚合 POST 请求 +8.78%（区间不重叠）；握手服务端 RFC6455 +17.47%（区间不重叠）；解码 masked 文本帧 +16.16%（区间不重叠）。均来自本次完整 60 项，不用诊断或筛选成绩替换。

- **瓶颈证据**：控制组四字段查询 17.67%、名称比较 8.07%、值物化 10.46%、扫描器 25.40%；POST 扫描器 26.20%、存储转移 6.87%、对象池 17.33%。相同生产产物的最终复采中，四字段扫描器 28.95%、POST 扫描器 27.88%、存储转移 6.98%、对象池 20.59%；这是重复定位，不是优化前后差值。这些为可重叠的 CPU 栈比例，不是可直接拿到的加速。控制组 getByte、offsetReadable、checkPositiveOrZero 和名称比较在所检查的热调用点能够内联，不能仅由源码层数认定其为调用瓶颈，也未证明全部边界检查被消除。findFirstValue 原字节码 192 bytes，在四字段调用点因已编译为大方法而拒绝内联；委托候选缩至 20 bytes，已验证 findFirstValue/findFirstIndex/getValue 在相应 C2 调用点内联，但吞吐证据仍不支持保留。 旧采样符号与实际容器矛盾仍见上一轮，不据不匹配符号更换底层结构。
- **负向与内存结果**：相对 round100，吞吐下降至少 5% 的项：解码简单请求 Neta -12.37% / Netty -5.13%；解码简单响应 Neta -5.65% / Netty -10.74%；解码同长度非特殊头字段 Neta -13.44% / Netty -3.24%；解码轮换分段 chunked 请求（4 段） Neta -6.45% / Netty -3.29%；聚合大响应 Neta -5.37% / Netty -3.21%；握手客户端 RFC6455 Neta -6.71% / Netty -1.70%；握手服务端 RFC6455 Neta -6.68% / Netty -7.93%；解码部分 masked 文本帧（3 段） Neta -6.06% / Netty -2.38%；解码 Hixie 文本帧 Neta -5.40% / Netty -1.97%；解码分片文本消息 Neta -12.67% / Netty -1.31%。分配变化至少 8 B/op 的项：编码简单请求 224.695→200.695 B/op；编码 POST 请求 273.384→249.384 B/op；编码简单响应 273.384→265.383 B/op；握手客户端 RFC6455 4,016.001→3,984.001 B/op；编码 Hixie 文本帧 121.379→97.379 B/op；编码文本消息自动分片 159.902→135.902 B/op。跨轮变化不能直接归因本轮代码；本轮候选均未增加每字段对象、比较缓冲或池容量。本轮未测 RSS、存活堆、多线程和突发积压；握手及部分 WebSocket B/op 包含 Invocation 夹具。
- **下一轮主线**：本轮停止继续堆叠比较表达式与方法委托的微调。优先做扫描工作量实验：HttpHeaderStreamingScanner 当前先找换行再找冒号，字段名前缀有重复扫描；尝试在模块内部合并定界扫描，但须与现有按 8 字节查找对照，不能先验认定单遍更快，也不增加 ByteBuf 专用接口。POST 则逐请求核对扫描批次、Storage 获取/回收和 retain/release 次数，再评估减少跨包临时头字段存储的创建与合并周转，不跳过释放或通过更改池容量抬高均值。四字段值物化的重复处理也需检查。上述均为下一轮待验证方向，本轮没有实现；结构实验继续保护首次/重复读取、12/32 字段、可变原始名称、分段和 chunked，不复活已否定的两个候选。 保留所有权、未物化字段可变性、错误和事件语义；不增加名称/长度白名单或协议专用 ByteBuf 接口。POST 仍是多批头字段与六包调度，不是多块正文复制基准。masked 文本的历史回退及优势不足继续作为保护项，不用本轮均值覆盖旧负向结果。
