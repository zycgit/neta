文档
1. NetListen 在 TCP 模式下会暂停接收新的传入链接，在 UDP 模式下来自新客户端的数据包会被丢弃，已经建立通道的远程数据会持续接收。
2. UDP 无法感知连接是否关闭，因此用户需要通过例如 心跳等机制处理 UDP 的 close。
3. UDP 模式下同样支持 reject 机制。
4. 使用 DTLS 时 UdpSoConfig 的 soSndBuf 和 soRcvBuf 需要大于 1280，否则会抛出 java.net.SocketException: Message too long 异常。
java.net.SocketException: Message too long
5. DTLS 下必须保证封包完整性，因此在使用 SSL 时切记不要对 DTLS 的封包进行拆分，否则会导致数据发送和接收完全停滞并且没有明显报错。
     - DTLS 协议中传输过大的封包建议在业务层对封包进行拆分并实现分包重传机制。
6. VrtTransfer 由于实现机制问题，无法模拟背压情况。

高优先
01. 背压机制 pipline 的输入/输出 队列容量是有界的，导致数据接收时如果通道没有可用槽需要暂停接收，目前会报错
02. SoContextService 的 asyncUnsafeCloseChannel 方法调用需要在 review
03. 整个系统的 异常传导机制需要在 review
04. 如果 pipline 为空 ByteBuf 会直接丢弃，目前没有关闭，在 pool 下会有内存泄漏问题。

次优先
01. ProtoStatistical 整合到 NetMonitor 中
02. IP 白名单机制
04. 协议路由，用来支持 NPN/ALPN
05. 通过 SSL 参数支持 peerHost 能力
06. ByteBuf 大文件 或输入输出流的 传输
07. PipeRoute
08. 流量控制
09. SoConfig 类还未完成英文化
10. SSL 证书兼容 PKCS12
11. pipline 需要支持分叉式的以便可以支持复杂协议树，可以使用 event 来实现，工作在协议层之上
12. 需要一个 CompositeByteBuf 来协助多个 ByteBuf 的操作。
13. 需要将 ProtoRcvQueue 到 CompositeByteBuf 的代理操作接口，从而屏蔽底层 ProtoRcvQueue 的一些列操作。如 ByteBuf 脱管造成内存泄漏的问题
14. 需要实现内存托管，简化资源释放。
15. 需要 owner 机制避免并发操作。
16. 需要一个流量心跳机制，用来检测对端是否还活着，例如在处理 UDP 连接时，服务器可以在某个特定时间时主动关闭连接
17. 优雅关闭（需要测试）
