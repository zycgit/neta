ProtoStack 是 Neta 的连接级处理模型。它把多个 Handler 串成一条有方向、有状态、可切换分支的处理链，用来承接字节输入、协议编解码、网络事件、异常传播和回写输出。

如果只看外形，管线可以先理解成一条沿连接展开的固定处理链。

```text
Inbound bytes / events
    |
    v
  +------------+     +------------+     +------------+     +------------+
  | handler-1  | --> | handler-2  | --> | handler-3  | --> | handler-4  |
  +------------+     +------------+     +------------+     +------------+
    ^                                                           |
    |                                                           v
    +------------------- outbound write / flush ----------------+
```

如果从双工协议栈的角度看，它更接近下面这个样子。

```text
         inbound phase                        outbound phase

socket read
  |
  v
[ RCV_UP ] --> [ decoder ] --> [ router ] --> [ app handler ]
                            |
                            v
[ SND_DOWN ] <-- [ encoder ] <-- [ writer ]  <-- [ SND_UP ]
  |
  v
socket write
```

这两张图表达的是同一件事：一条连接只有一个顶层 ProtoStack，数据和事件会在这条结构里按照既定方向传播；必要时可以在中间切换路由、切换分区、切换状态，但不鼓励在运行期任意改写整条结构。

## 管线长什么样

Neta 的管线由一个个 Handler 组成。它们可以是单工器，也可以是双工器，但对管线来说都只是“链上的节点”。

典型结构通常包含几类节点：

- 传输层节点：处理原始字节、分帧、粘拆包、聚合。
- 协议层节点：处理编解码、握手、升级、安全层。
- 控制节点：处理状态切换、路由切换、分区切换、背压。
- 应用节点：接收已经稳定的协议对象，执行业务逻辑或回包。

例如一个常见的服务器侧协议栈可以写成下面这样。

```java
manager.bind(address, ctx -> {
  ctx.addLast("frame", new LineBasedFrameHandler(4096, false));
  ctx.addLast("codec", new StringHandler());
  ctx.addLast("app", appHandler);
}, SoConfig.TCP());
```

这段结构说明了三个关键点：

- 先处理边界，再处理协议对象，最后进入业务。
- 每个节点只负责一层语义，避免一个 Handler 同时兼顾拆包、路由、业务分发。
- 结构在初始化阶段一次性装好，运行时主要切行为，不切拓扑。

## 三大流

讲管线一定绕不开三大流：数据流、事件流、异常流。它们共享同一条结构，但触发条件和传播语义不同。

### 数据流

数据流负责把网络输入转换成协议对象，再把业务输出转换回网络输出。

```text
inbound bytes
  |
  v
[frame] -> [decode] -> [aggregate] -> [app]
                    |
                    v
                  [encode]
                    |
                    v
                outbound bytes
```

它的特点是：

- 上行通常从连接底部进入，逐个经过解码、聚合、路由、业务处理。
- 下行通常从逻辑上层发起，经过编码或封包后回到底层输出。
- 同一条消息不一定要经过所有节点，路由切换、分区切换或 Skip 一类控制都可能改变后续路径。

### 事件流

事件流负责传递连接状态和控制语义，例如连接建立、关闭、半关闭、可写状态变化、用户自定义事件。

```text
network event
  |
  v
[handler-1] -> [handler-2] -> [handler-3] -> [handler-4]
```

它的特点是：

- 事件本身不一定携带业务数据，但会改变 Handler 的行为解释方式。
- 很多协议阶段变化并不是靠改结构实现，而是靠事件驱动状态切换。
- 背压、水位变化、关闭语义这类连接级能力，本质上也依赖事件流传播。

### 异常流

异常流负责处理数据流或事件流中的失败情况。它不是另一条独立管线，而是同一条管线上的错误传播过程。

```text
message / event
  |
  v
[handler-1] -> [handler-2] -> [handler-3 throws error]
                    |
                    v
               switch to exception flow
                    |
                    v
           [handler-3.onError] -> [handler-2.onError] -> [handler-1.onError]
```

它的特点是：

- 常规处理抛错后，会切入异常传播。
- 异常仍然沿管线传播，而不是直接跳出整个连接模型。
- 处理器可以在异常流里记录、转换、恢复或终止错误。
- 如果通过异常持有器清除了异常状态，后续可以回到常规传播。

## 运行方式

把三大流放在一起看，ProtoStack 的运行方式可以概括成下面这张图。

```text
        +-------------------------+
socket read --->|     inbound dispatch    |----+
event fire ---->|   message / event in    |    |
        +-------------------------+    |
                         v
                    +----------------+
                    |   handlers...  |
                    +----------------+
                       |    |     |
                       |    |     +--> error -> exception flow
                       |    +--------> user event propagation
                       +-------------> data propagation

app write -----------------------------------------------> outbound dispatch -> socket write
```

这里有几个容易混淆但很重要的点：

- 管线不是简单的单向链，它天然包含上行和下行两个方向。
- 事件和数据共用一套结构，但每个 Handler 可以对不同输入类型给出不同反应。
- 异常不是脱离模型的补丁，它是内建的第三种传播语义。

## 流转控制

流转控制决定了某个 Handler 执行结束后，下一个步骤是什么。顺序执行只是默认情况，不是唯一情况。

```java
public ProtoStack onMessage(PipeContext context,
    ProtoRcvQueue<ByteBuf> src,
    ProtoSndQueue<String> dst) {
  return ProtoStack.Next;
}
```

Neta 提供的控制语义可以概括为下面几类：

- Next：按既定顺序继续传播。
- Retry：立即重试当前处理步骤。
- Again：当前方向走完后回到起点重新来一轮。
- Back：当前方向走完后回到当前节点再来一轮。
- Restart：中断当前传播并从当前方向起点重新开始。
- Skip：跳过中间剩余节点，直接进入当前阶段末尾。
- Interrupt：中断传播并抛出错误。

这些控制语义的意义不在于“更灵活”，而在于把连接级行为写成显式协议动作，而不是散落在外部回调里的隐式跳转。

## 一般用法

大多数场景下，设计管线时遵循下面的顺序就足够了。

### 1. 先确定固定结构

先定义这条连接稳定存在的处理层次，例如：

- 帧边界处理。
- 编解码。
- 聚合。
- 协议控制。
- 应用处理。

如果一个能力只在连接建立时决定一次，它通常应该直接成为固定结构的一部分。

### 2. 再决定运行期变化放在哪里

运行期仍然允许变化，但变化对象应当是受控的：

- 状态切换：用于表达握手前后、明文到 TLS、升级前后这类阶段差异。
- 路由切换：用于在预定义分支之间切换当前生效路径。
- 分区切换：用于在同一连接内隔离多路并发子链。

其中路由管线和分区管线都很重要，但它们有各自的专门页面，这里只保留总览。

```text
         +---------------------+
inbound -------->| ProtoRoutingDuplexer|---+--> branch A
         +---------------------+   |
                       +--> branch B
                       |
                       +--> branch C
```

```text
         +-----------------------+
inbound -------->| ProtoPartitionDuplexer|---+--> partition 1
         +-----------------------+   |
                         +--> partition 2
                         |
                         +--> partition 3
```

路由强调的是“当前走哪条固定分支”，分区强调的是“同一连接里并存多少条相互隔离的局部子链”。

### 3. 最后把业务留在管线边界之后

如果输入已经变成稳定的业务对象，后续重点只是分发、聚合、回调、落库或异步任务，那么通常应该让它离开 Pipeline，进入 subscribe 或业务服务层。

## 静态结构原则

Neta 后续以如下原则约束 ProtoStack 的结构演进。

> 结构只能在初始化期确定；运行期只能切状态、切路由、切分区，不能随意改结构。

这样做的原因很直接：

- 动态增删 Handler 会让协议生命周期难以追踪。
- 运行期改链容易和异常传播、半关闭、重入、背压耦合。
- 结构一旦不稳定，测试矩阵和排障成本都会快速上升。

与之对应，静态结构的收益也很明确：

- 装配边界固定，初始化期做什么一眼可见。
- 运行期变化可以通过状态、路由、分区显式建模。
- 文档、测试、可视化和问题定位都更容易收敛。

沿着这个原则，可以把 ProtoStack 的职责收敛为三类：

- 静态结构：由 ProtoInitializer 在连接建立或分支初始化时一次性装配完成。
- 运行期切换：通过状态、路由、分区表达协议阶段变化。
- 业务外移：稳定消息对象离开管线，交给业务层决定后续编排。

当前接口层已经按这个边界完成了第一步收口：ProtoInitializer.config(...) 只接受 ProtoBuildContext，不再保留 ProtoContext 兼容签名。

## 基于容量的反压机制

ProtoStack 不只是做编解码和分发，它还承担连接级流量控制。Neta 中一个重要特性是基于容量的反压机制。

可以先把它理解成“当管线内部来不及消化输入时，连接会主动收紧推进速度，而不是让消息无限堆积”。

```text
socket read speed  >>> pipeline consume speed
     |
     v
   inbound queue size grows
     |
     v
   reach capacity threshold
     |
     v
   trigger backpressure event
     |
     v
   slow down / suspend / recover later
```

它主要解决几个问题：

- 避免单条连接在高峰期无限制占用内存。
- 避免某个慢 Handler 把整条连接拖入失控堆积。
- 让恢复动作有明确边界，而不是在外部靠猜测补跑。

这类反压能力属于连接级语义，所以它天然应当留在 Pipeline 内，而不是交给业务层事后补救。

## 设计边界

判断一个能力是否应该放进管线，可以用下面这组问题快速筛一遍：

1. 它是否仍然依赖连接状态、传播方向、握手阶段或容量控制。
2. 如果依赖，它是固定结构、状态变化、路由变化还是分区变化。
3. 如果面对的已经是稳定消息对象，它是否更适合离开管线。

判断标准可以再压缩成一句话：

- 还属于连接级协议语义，就留在 Pipeline。
- 已经变成稳定业务语义，就离开 Pipeline。

这就是 Neta 的管线模型：一条静态装配、运行期受控切换、同时承载数据流、事件流和异常流的连接处理结构。
