在 Neta 的 Handler 模型里，连接上的处理过程不能只看成“消息一路往下走”。

更准确的理解方式是：同一条 Handler 链同时承载三种传播语义。

- 数据流：负责承接输入输出数据。
- 事件流：负责承接状态变化和控制信号。
- 异常流：负责承接失败和恢复。

这三种流共享同一套 Handler 结构，但进入点、回调方法和传播目的都不同。

## 总体结构

先看一个总图。

```text
socket read / app write / network event / error
                    |
                    v
      +---------------------------------------+
      |          same handler chain           |
      | [H1] -> [H2] -> [H3] -> [H4]          |
      +---------------------------------------+
          |        |                  |
          |        |                  +--> exception flow
          |        +---------------------> event flow
          +------------------------------> data flow
```

这张图要表达的重点只有一个：三大流不是三套完全独立的 Pipeline，而是在同一条 Handler 链上以不同方式推进。

## 数据流

数据流是最直观的一种流。它负责把网络输入交给 Handler 处理，再把处理结果继续送往后续节点或回写到底层连接。

```text
RCV
socket read
   |
   v
[H1] -> [H2] -> [H3] -> [H4]

SND
[H1] <- [H2] <- [H3] <- [H4]
                           |
                           v
                      socket write
```

从 Handler 视角看，数据流有几个关键特征：

- 它主要通过 `onMessage(...)` 承接。
- 它天然有方向，接收和发送并不是一回事。
- 它通常承载的是字节、帧、协议对象或业务对象。

典型过程可以概括为：

```text
ByteBuf -> frame -> protocol object -> app message -> response -> encoded bytes
```

这意味着一个 Handler 的职责通常是下面几种之一：

- 透传数据，不改变对象。
- 把上游对象转换成下游对象。
- 聚合或拆分数据。
- 在合适时机向下游发送新对象。

如果当前处理器面向的是稳定业务对象，而不是连接级协议状态，那么它往往已经靠近 Pipeline 的边界了。

## 事件流

事件流负责传递“不是普通消息，但又必须让协议层知道”的东西。

典型例子包括：

- 连接激活。
- 半关闭。
- 握手完成。
- 编解码模式切换。
- 用户自定义控制事件。

从 Handler 视角看，事件流主要通过 `onEvent(...)` 承接。

```text
SoEvent
  |
  v
[H1] -> [H2] -> [H3] -> [H4]
```

它和数据流的区别在于：

- 数据流承载“要处理的内容”，事件流承载“要感知的状态变化”。
- 数据流通常进入队列语义，事件流通常不进入普通消息队列。
- 数据流主要影响对象转换，事件流主要影响 Handler 行为。

一个常见场景是：某个下游协议层完成握手后，通过事件流通知上游或旁边的协议层切换模式。

```text
[ssl handler] -- fireEvent(...) --> [http codec] --> [app handler]
```

这类传播的核心价值在于：协议层之间可以通过显式事件协作，而不需要靠共享状态和隐式约定互相猜测。

关于事件对象模型、触发入口和跨分支传播规则，见 [network_event.md](network_event.md)。

## 异常流

异常流是 Handler 模型里第三种必须单独理解的传播语义。

当数据流或事件流中的某个处理步骤失败后，处理过程不会简单地“直接炸掉并结束”，而是切换到异常传播。

```text
message / event
    |
    v
[H1] -> [H2] -> [H3 throws error] -> [H4]
                 |
                 v
            exception state
                 |
                 v
      [H3.onError] -> [H2.onError] -> [H1.onError]
```

从 Handler 视角看，异常流的关键点是：

- 它主要通过 `onError(...)` 承接。
- 它不是脱离上下文的日志回调，而是协议栈的一部分。
- 它会沿当前结构继续传播，直到被处理、恢复或中断。

这意味着 `onError(...)` 的职责不只是打印异常。它通常可以做几类事情：

- 把底层异常转换成更高层协议错误。
- 做资源清理。
- 决定是否关闭连接。
- 清除异常状态后回到常规处理。

如果当前 Handler 没有清除异常状态，那么后续处理器通常会继续停留在异常传播阶段，而不是重新进入正常的 `onMessage(...)`。

## 三大流之间的关系

三大流并不是互不相干，它们经常互相切换。

最常见的切换关系如下：

```text
data flow -- throws --> exception flow
event flow -- throws --> exception flow
event flow -- changes state --> later data flow uses new behavior
data flow -- fireEvent --> event flow
```

也就是说：

- 数据流可能触发事件流。
- 事件流可能改变后续数据流的解释方式。
- 数据流和事件流都可能切入异常流。
- 异常流处理完成后，还可能回到常规流。

这也是为什么 Neta 的 Handler 设计强调生命周期和方向，而不是只看“收到一条消息该怎么办”。

## 怎么区分当前逻辑属于哪一流

写 Handler 时，可以用下面这组问题快速判断。

### 1. 它处理的是消息内容还是状态变化

- 如果处理的是字节、帧、协议对象、业务对象，通常属于数据流。
- 如果处理的是握手完成、连接关闭、模式切换、控制通知，通常属于事件流。

### 2. 它是在处理失败后的补救路径吗

- 如果当前逻辑是在某个失败之后执行，用于转换错误、清理资源或恢复状态，通常属于异常流。

### 3. 它影响的是对象本身还是后续行为

- 改对象，多半属于数据流。
- 改行为，多半属于事件流。
- 处理失败，多半属于异常流。

## 一般用法建议

把三大流拆开理解后，写 Handler 会清晰很多。

建议遵循下面几个原则：

- 数据转换尽量放在 `onMessage(...)`，不要把正常数据处理塞进事件流。
- 协议状态切换尽量通过事件流表达，不要靠共享布尔值偷偷改变行为。
- 异常处理尽量放在 `onError(...)`，不要把恢复逻辑散落在普通消息路径里。
- 如果某个能力仍然依赖连接状态、传播方向和协议阶段，它就应该留在 Handler / Pipeline 模型内。

可以把一个设计良好的 Handler 理解成下面这种分工：

```text
onMessage(...)  -> 处理数据
onEvent(...)    -> 处理状态变化
onError(...)    -> 处理失败与恢复
```

这三条线分清楚之后，Handler 的职责边界、调试路径和测试场景都会明显更稳定。
